## 一、串口这条路已经断了

指南 Day 26 写的是"打开串口、实时读取 JSON"。但车从 Day 24 起就脱离 USB 自己在跑了，自由跑的时候**根本不存在串口设备**——要去读串口就得插线，插上线车又被拴住。而实时绘图的意义恰恰是看它自由跑。Day 22 记过"串口这条路有窗口期"，今天就兑现了。

换成 Wi-Fi 之后工序反而更少：Day 25 的实验 3 已经把同一份 JSON 放到 HTTP 上了，Python 端只要拉一次 `/data`，**固件一行都不用改**。数据通道从"一条线"变成"一个 URL"：

```
serial.Serial('/dev/cu.usbmodemXXX', 115200)   →   requests.get('http://192.168.0.5/data')
ser.readline()                                 →   r.text
```

同时也少一件事：这份 `/data` 的 JSON **只存在于 HTTP 通道**。串口打出来的是人读的整句（`#699 28.0 cm`），要让机器从串口读 JSON 就得改固件再烧一次——而板子上已经跑着能用的服务了，没有理由为了一份同样的数据去动它。所以今天的仓库里没有新的 `.ino`：`day-26/` 下只有一个 Python 文件，固件在 [`day-25/实验3-WebServer/`](../day-25/实验3-WebServer/)。

解析逻辑几乎原样：Day 22 的 `serial_logger.py` 是"读到一行以 `{` 开头的才算"，这里是"响应体以 `{` 开头才算"——半包数据在网络路径上同样存在，板子重启、Wi-Fi 重连的瞬间会吐半个响应体，过滤必须做，不能指望一次 `get()` 拿到的就是完整 JSON。

## 二、指南代码的三处不能照抄

指南那段 `serial.Serial()` + `d['sensor']` + `set_ylim(0, 4095)` 的参考代码，拿过来有三处对不上：

**① `d['sensor']` — 字段名对不上。** 车上只有 HC-SR04，`/data` 的字段叫 `cm`：

```json
{"cm":47.6,"rssi":-18,"up":8521,"n":41839,"ip":"192.168.0.5"}
```

照抄会 `KeyError`。这也说明一件事：**远端的数据约定是固件定的，读之前得先看一眼它到底吐什么**，而不是先写解析。

**② `ax.set_ylim(0, 4095)` — 这是 ADC 的量程，不是距离的。** 4095 是 12 位 ADC 满值，HC-SR04 出来的是厘米。写死 4095 的结果是一条贴着 x 轴的直线，视觉上等于没画。y 轴上限改成跟着数据走（`max(known) * 1.15 + 5`），下限钉死在 0——距离不可能为负，否则自动缩放会被一片 −1 拉出一个难看的负区间。

**③ x 轴一直在涨，跑十分钟曲线就压成一条线。** 指南写的是 `ax.set_xlim(0, max(100, len(data)))`——横轴随历史变长，全部采样挤在同一个窗口里。实时监控要的是**滚动窗口**，横轴只看最近 60 秒，老数据滑出去：

```python
xmax = xs[-1]
ax.set_xlim(max(0.0, xmax - WINDOW_S), max(WINDOW_S, xmax))
```

外加两条补强：`deque(maxlen=2000)` 兜住内存（跑一夜不往数组里塞两百万个数），以及按剩余时间睡而不是死等——固件 200 ms 才测一次，请求本身也要花时间：

```python
spent = time.monotonic() - t0
time.sleep(max(0.0, args.interval - spent))
```

## 三、两种"没数"：−1 是结论，NaN 是没采到

这是今天最需要想清楚的一处。HC-SR04 有两种拿不到数的方式，含义完全不同：

| 值 | 物理含义 | 图上 | CSV |
|---|---|---|---|
| `−1.0` | **前方有超声吸收面**（墙、窗帘、软布），回声弱到 6000 µs 都没回来 | 断线（NaN） | 照原值写 `−1.0` |
| NaN | **根本没采到**：网络失败，或响应体不是合法 JSON | 断线 | 留空 |

`pulseIn` 超时返回 0，固件转成 −1.0。这个 −1 **是有信息的**：它是一条有效的测量结论。所以 CSV 里必须留着原值——Day 22 的 `serial_logger.py` 就是这么存的（`data.get("dist_cm", "")`，不过滤）。

但图上不能让它落下去。把 −1 画进去，会在曲线底部凿出一根垂直的假尖刺，看起来像"距离突然归零再跳回来"，读图的人会以为车贴脸了。图上画断线，文件里留原值——两处各取所需。脚本把两者分开计数（`timeouts` vs `drops`），标题里一起显示，跑完的汇总行也是两个数：

```
共 222 次轮询：有效 180、超时(有吸收面) 42、掉线(没采到) 0
```

那 42 个超时在图上是一片空白，但空白本身就是结论。

## 四、Plotly Dash 为什么不做

指南说"可选：用 Plotly Dash 做 Web 仪表盘"。这一步跳过，因为 **Day 25 实验 3 已经把它做完了，而且做得更好**：

- 那个页面是**板子自己发的**，不依赖电脑上开着 Python 进程；手机关同一个 Wi-Fi 直接就能看
- Dash 要另起一个 Web 服务、另开一个浏览器标签指向电脑，还得多装 `dash` + `plotly` 两个包
- 唯一比实验 3 强的是"能看历史"，而这个脚本的 PNG + CSV 已经覆盖了

同一个需求，先用已有实现，不够再加。Day 25 说的"同一份 JSON 有两个消费者"，到这里两个都兑现了。

## 五、踩的坑

| 现象 | 原因 | 解决 |
|---|---|---|
| 存出来的 PNG 标题是一排豆腐块，刷一屏 `Glyph missing from font(s) DejaVu Sans` | 标题写的是中文，matplotlib 默认的 DejaVu Sans **没有汉字字形**；而 matplotlib **不内置** CJK 字体 | `pick_cjk_font()` 从系统已装的字体里挑第一个（PingFang SC → Heiti SC → Songti SC → …）塞进 `plt.rcParams["font.sans-serif"]`；同时把 `axes.unicode_minus` 关掉——负号在部分中文字体里也是缺的 |
| `--host esp32s3.local` 跑起来几乎每次轮询都掉线 | 光是**解析 mDNS 名字就要 ~5 秒**，直连 IP 只要 0.1 秒 | 采数据用 `--host 192.168.0.5`；mDNS 名留给人开浏览器 |
| 把 `requests.get(..., timeout=2.0)` 当保险，超时却没生效 | `getaddrinfo()` 是阻塞调用，**socket 超时拦不住它**——实测 `timeout=2.0` 的请求仍跑满 5.12 s 才返回 | DNS 慢不能靠 timeout 救，只能绕开：直接用 IP |
| SSH / 纯终端里跑，脚本直接退出 | 没有可用的显示后端，matplotlib 落到 `agg`，画不出窗口 | 启动时判断后端，落在 `agg / pdf / svg / …` 里就早失败早说，而不是"跑起来了但没窗口" |
| `.venv` 的 Python 3.14 没有 `_tkinter` | Python 编译时没带 tcl/tk 开发头，事后 `pip install` 补不回来 | 只检查后端、**不指定**后端：macOS 默认的 `macosx` 是好的，强行写 `TkAgg` 反而会把能用的环境弄坏 |

## 六、测试结果

对 `192.168.0.5` 实采 44.6 秒、222 次轮询（`--interval 0.2`，和固件 200 ms 的测量间隔对齐，再快也是重复值）：

![远程实时距离曲线](./telemetry_plot.png)

汇总：`共 222 次轮询：有效 180、超时(有吸收面) 42、掉线(没采到) 0`。CSV 存 [`wifi_run.csv`](./wifi_run.csv)（222 行，字段 `timestamp, t_s, cm, rssi, up, n`，−1 原样保留，真没采到的行 `cm` 为空）。

**掉线 0**：222 × 0.2 s = 44.4 s，一个都没漏。同一个局域网里拉一个 60 字节的 JSON 是可靠的。RSSI 全程 −17…−22 dBm，和 Day 25 记的 −17 dBm 一样稳。

曲线不是一条平线，有三件事值得看：

**① 42 个超时不是均匀撒的，是成片的。** 它们集中在 5 段里，最长的一段在 t=16.41–19.38：**连续 15 个采样全是 −1，持续 2.97 秒**，而它前后都是 48–59 cm 的正常读数。成片的 −1 才符合"前方出现吸收面"——如果 −1 是随机噪声，应该零散分布，而不是连续三秒一个都不回。这正是 Day 12 用手在传感器前晃动、Day 25 那 1132 次采样里周期性"超出量程"的同一条物理规律，第三次出现了。图上这段就是 NaN 造成的一处空白。

**② 读数掉到 15 cm 以下的共 13 段：4 段是清一色的 −1（就是上一段说的超时），其余 9 段带着真实近距读数。** 最长的一处在 t=36.28–40.68（23 个采样，4.4 秒）：读数从 42 cm 一路掉到 **2.0 cm**，并在 2.0–4.6 cm 之间停留了约 2 秒，再退回来。HC-SR04 手册标的下限就是 2 cm，这几样本该就在盲区边缘——**近场读数能不能信，是个要单独验证的问题**，不适合直接喂给避障逻辑。这些下探在图上是一串尖尖的 V 形。

**③ 近场读数本身在抖。** 同一处下探里，相邻两个 200 ms 采样能差出 3 倍（2.0 → 7.4 → 2.0 cm）。超声波束很宽，近处稍有移动落点就变，这是物理特性不是噪声，滤波之前先知道抖动幅度是必要的。

关窗口或 Ctrl+C 都会走 `finally`：先关 CSV，再 `fig.savefig()` 存一张 PNG。无头环境下没法真的按 Ctrl+C，所以验证办法是**给子进程发 `SIGINT`**——它会在脚本里变成 `KeyboardInterrupt`，`finally` 照常执行，产物和手动停一样。

⏭️ 进阶：把轮询改成 `requests.Session()` 复用连接。现在每次 `get()` 都要重新建连，0.1 秒里有一部分花在这上面

⏭️ 进阶：给曲线加一次低通。近场抖动幅度有 3 倍（见测试结果 ③），喂给避障状态机之前得先压一压
