## 一、舵机和昨天的 TT 马达差在哪

| | Day 19 TT 马达 | Day 20 SG90 舵机 |
|---|---|---|
| 控制量 | 转速（连续旋转） | **角度**（0°~180° 定位） |
| 反馈 | 无，开环 | 内部电位器测位置，**闭环在舵机里** |
| 需要的驱动 | H 桥（要换向） | 不需要，单线 PWM |
| 给错指令的后果 | 转太快 / 转不动 | 堵转发热，可能烧 |
| 额定电压 | 3V | **4.8V**（SG90 标称） |

一句话：**马达是"给电压就转"，舵机是"给角度就停在那儿"。** SG90 拆开是电机 + 减速齿轮 + 位置电位器 + 控制板四件套，位置闭环由舵机自己做完了，外部只发目标角度。这也是为什么它叫"舵机"而不是"电机"。

## 二、信号协议：同一个 PWM，完全不同的含义

这是今天最该记住的一句：

> **Day 19 的 PWM 里，脉冲宽度编码的是"平均电压 = 转速"；Day 20 的 PWM 里，脉冲宽度编码的是"绝对位置 = 角度"。波形看着一样，物理含义毫无关系。**

参数对比：

| | Day 19 电机 | Day 20 舵机 |
|---|---|---|
| 频率 | 5000Hz（5kHz） | **50Hz** |
| 周期 | 0.2ms | **20ms** |
| 编码量 | 高电平占比 | 高电平**绝对宽度** |
| 低电平是什么 | 另一半占空比，参与平均 | 纯间隔，"没有指令" |

协议本体：

```
一个周期 20ms ────────────────┬─────────────┬──────────
                              │             │
                              └─ 0.5ms ─┘   = 0°
                              └─ 1.5ms ─┘   = 90°
                              └─ 2.5ms ─┘   = 180°
                    剩下的 ~17.5ms 低电平无所谓
```

- **只有高电平的宽度有意义**，剩下的低电平是间隔。舵机在每个脉冲的上升沿重新读一次宽度。
- 0.5ms~2.5ms 是 SG90 的量程，不是协议规定。不同舵机的端点值不同（有的 0.5~2.4ms），通用舵机测试仪上的"中点 1.5ms"是共识。
- 频率必须是 50Hz：舵机内部控制回路需要约 20ms 采样一次。发快了它来不及响应，发慢了保持不住会"抖"。
- 不需要方向控制，所以**不需要 H 桥** —— 昨天那套真值表今天整张作废，这是驱动电路的第一次"变薄"。

## 三、供电：Day 20 最大的坑

### 信号线可以直接接 3.3V，功率线不行

SG90 的高电平阈值一般 2.0~2.5V，ESP32 的 3.3V 输出对它就是可靠高电平 —— **信号线（黄色）直接接 GPIO，不需要电平转换**。这和 Day 17 特意挑宽电压版 HC-SR04 省掉电平转换是同一个思路。

但红线必须外接 5V：

```
SG90 空载      ~100mA
SG90 带负载    200~300mA
SG90 堵转      700mA 以上
ESP32 3V3 脚   建议不超过 500mA（且与板载逻辑共用）
```

舵机不是逻辑器件，是机电执行器。**"逻辑电平兼容"不等于"功率兼容"** —— 这是 Day 20 供电上唯一需要记住的判据。

### 三个供电选项

| 方案 | 做法 | 评价 |
|---|---|---|
| ① ESP32 板 5V / VIN 脚 | 舵机红线接板子的 5V 脚，USB 供电 | 省线，但 USB 只有 500mA。**堵转瞬间会把 USB 端口拉欠压，可能让整块 ESP32 重启**，且重启后舵机又堵转，进入循环 |
| ② 外接 3~4 节 5 号（4.5~6V）+ 共地 | 电池盒独立供舵机 | ✅ 推荐，舵机电流不碰开发板 |
| ③ 映棠 6V 电池盒 | 用那件带盖带开关的 4 节盒 | 6V 在 SG90 工作范围（约 3.5~6V）内，能跑，且舵机会更快更热。**正好给那件"待裁决"的 6V 盒找了个正当用途** |

SG90 标称 4.8V，接 6V 是超压 25%（比 Day 19 的 6V → 3V 超压一倍轻得多）。短时调试可以，长期不建议。追求稳妥用 3 节 5 号 = 4.5V。

### 共地和 Day 19 一样是头号嫌疑

```
外接电源 + ── 舵机红线
外接电源 − ──┬── 舵机棕线
             └── ESP32 GND
```

少共地时，GPIO 发的高电平在舵机里没有参考点，表现是"代码在跑、串口正常、舵机纹丝不动"—— 和 Day 19 一模一样的症状。

## 四、duty 换算（数学，不难但值得推一遍）

目标：50Hz、ESP32-S3 能给的 14 位分辨率下，把 0~180° 变成 `ledcWrite` 要的 duty。

```
周期        = 1 / 50Hz            = 20ms = 20000us
14 位步数   = 2^14                = 16384
每步时长    = 20000 / 16384       ≈ 1.221us
```

所以 `duty = 脉冲宽度(us) × 16384 / 20000`，代入三个特征点：

| 角度 | 脉冲宽度 | duty |
|:---:|:---:|:---:|
| 0° | 500us | `500 × 16384 / 20000 =` **410** |
| 90° | 1500us | `1500 × 16384 / 20000 =` **1229** |
| 180° | 2500us | `2500 × 16384 / 20000 =` **2048** |

代码里就一行：

```cpp
float us = US_MIN + (US_MAX - US_MIN) * deg / 180.0;
return (int)(us * 16384.0 / 20000.0 + 0.5);
```

### 为什么是 14 位，而不是教程里的 16 位

**ESP32-S3 的 LEDC 硬件上限就是 14 位。** 用编译探针把 `SOC_LEDC_TIMER_BIT_WIDTH` 的值逼到编译错误里打印出来，实测就是 `14`：

```cpp
template <int N> struct Reveal;
Reveal<SOC_LEDC_TIMER_BIT_WIDTH> r;   // 报错消息里会显示模板实参 = 14
```

所有舵机教程写的 `ledcAttach(pin, 50, 16)` 是**初代 ESP32**（上限 20 位）的参数。照抄到 S3 上，`esp32-hal-ledc.c` 里这一行直接把它挡掉：

```c
if (resolution == 0 || resolution > SOC_LEDC_TIMER_BIT_WIDTH) return false;
```

**返回 false，但不打任何日志。** 于是串口照常打印、循环照常跑，舵机纹丝不动 —— 排查时它看起来完全像"接线问题"。

### 那 14 位够用吗

够。反过来算 8 位（Day 10、Day 19 呼吸灯用的就是 8 位）：

```
8 位 = 256 步，每步 20000 / 256 = 78us
```

一步 78us，而 0° 到 180° 全程只差 2000us —— **8 位的一个台阶就等于 7°**，舵机只能在 0、7、14、21… 这种糙度上跳，完全不可用。

14 位每步 1.221us，全程 1638 个台阶 ≈ **0.11°/步**，比舵机自身的机械回差还细。所以 14 位不是妥协，是够用且是上限。

**同一个 ESP32 LEDC 外设，Day 10 用 8 位、Day 19 用 8 位、今天必须往上加，但 S3 只给到 14 位** —— 分辨率不是口味问题，是被"要表达多细的东西"和"硬件能给多少"两边夹出来的。

[`实验2-串口控制角度.ino`](./实验2-串口控制角度/实验2-串口控制角度.ino)：串口输入 0~180 回车即转，非数字/越界拒绝。

### API 版本陷阱

《逐日指南》的参考代码用的是**旧 API**，直接抄编译不过：

```cpp
ledcSetup(0, 50, 16);          // ❌ Core 3.x 已删除
ledcAttachPin(SERVO_PIN, 0);   // ❌ 同上
ledcWrite(0, duty);            // ❌ 按通道号写
```

本项目改成 Core 3.x 的新写法：

```cpp
ledcAttach(SERVO_PIN, 50, 14); // ✅ 频率 + 分辨率在这里（S3 上限 14 位）
ledcWrite(SERVO_PIN, duty);    // ✅ 按引脚写，没有通道号
```

和 Day 19 的 `TB6612FNG` 代码是同一套，只是频率从 5000 换成 50、分辨率从 8 换成 14。

### 自检只能信 bool 返回值

`ledcAttach` / `ledcWrite` 都返回 `bool`，这是**唯一可靠的硬件判据**。曾经用 `ledcRead()` / `ledcReadFreq()` 复核过，两个都会骗人：

- `ledcReadFreq()` 从时钟分频寄存器反推频率，50Hz 这种极低频 + `LEDC_AUTO_CLK` 下常算出 **0Hz**；attach 明明成功它也报 0。
- `ledcRead()` 读的是**影子寄存器**，要等一个完整 PWM 周期（50Hz = 20ms）才同步。`ledcAttach` 后立刻读拿到的是残留值 —— 实测读到 **6**，而真实 duty 是 410，舵机其实转得好好的。

两个都误报过"失败"。结论：**false 才算数，回读值一律不看。**

### `Serial.parseInt()` 的三个坑

实验 2 里三处处理都是冲着它：

**① 超时返回 0，而 0 是合法角度。** 默认 1 秒超时，用户什么都没发时它也返回 0，会把舵机打到限位。代码用 `Serial.setTimeout(10)` 把等待压到 10ms。

**② 上一次输入的数字会粘住。** 回车符 `\r\n` 本身不是数字，`parseInt` 会跳过它们继续等，于是上一轮的"180"残留在缓冲区里被拼进下一轮。代码在解析后 `while (Serial.available()) Serial.read();` 把行尾读干净。

**③ 只解析到第一个数字就停。** 输入 `abc` 返回 0（碰巧是合法角度），输入 `12abc` 返回 12。所以范围判断不能只靠解析结果，非数字输入要靠"结果不可信"这个前提来兜 —— 实际教学演示里输入定长数字即可，真要健壮得自己写状态机逐字符读。

## 六、上机检查点

| 现象 | 判断 |
|---|---|
| 上电瞬间舵机"咯噔"跳到某个位置 | 正常。上电到第一次 `ledcWrite` 之间没有脉冲，舵机处于自由态，第一个脉冲到达时它会快速归位 |
| 不走指令时舵机是"绷住"的，用手拧不动 | 正常。模拟舵机没有指令时**保持最后位置**，不是松掉。松掉只有掉电一种情况 |
| 长时间停在固定角度，舵机不发热 | 正常。保持位置只需要很小的保持电流，不是堵转 |
| 用手强行把舵机扭住不放 → 很快发热甚至烫手 | ❌ **这是烧舵机最常见的方式**。堵转时电流冲到 700mA+ 全变成热 |
| 串口正常但舵机完全不动 | 头号嫌疑是没共地，其次是红线没接 5V |
| 舵机抖动、嗡嗡响、角度不到位 | 供电不足（USB 500mA 被拉垮）或红线接到了 3V3 |

### SG90 读不到实际角度

SG90 是**模拟舵机**，只有信号输入一根线，没有反馈输出。它内部那个电位器的信号不引出到外部 —— 所以和 Day 19 一样是开环：代码知道"我发了 90°"，不知道"它是不是真在 90°"。

想知道实际位置只能外加电位器或编码器，那是后面的内容。

## 七、实测

材料：[`实验1-自动摆动.MOV`](./实验1-自动摆动.MOV) ｜ [`实验1-串口打印.png`](./实验1-串口打印.png) ｜ [`实验1-电路图.png`](./实验1-电路图.png)

串口打印：

```
频率 50Hz / 分辨率 14 位 → 每步 1.221us
角度 0 / 90 / 180 → duty 410 / 1229 / 2048
[自检] GPIO18  attach=OK  write=OK   回读 duty=6 (期望 410)
[自检] LedcReadFreq=0Hz
{"angle":0,"duty":410,"us":500}
{"angle":90,"duty":1229,"us":1500}
{"angle":180,"duty":2048,"us":2500}
```

三条判读：

1. **`attach=OK`** —— PWM 起来了，舵机随之转动，视频里能看到它在 0°→180° 之间摆。
2. **duty 三点值 410 / 1229 / 2048** 与 §四 手算完全一致，`us` 字段回算的脉冲宽度也正好 500 / 1500 / 2500us。
3. **`回读 duty=6`、`LedcReadFreq=0Hz` 是假的** —— 同一时刻舵机明明在转。这两个回读函数已按 §五 的理由从自检里删掉。

实物接线：黄色信号线接 GPIO18，红/棕接外接电源轨，外接电源负极与 ESP32 GND 共地。

### 实验2：串口输入角度

材料：[`实验2-串口控制角度.MOV`](./实验2-串口控制角度.MOV) ｜ [`实验2-串口输入角度.png`](./实验2-串口输入角度.png)

串口监视器设为 115200 / 换行（Newline），依次输入 `0` `180` `90` `160` `30` `0`：

```
15:34:42.472 -> === 实验2：串口控制舵机角度 ===
15:34:42.472 -> [自检] GPIO18 attach=OK
15:34:42.472 -> {"angle":90,"duty":1229,"us":1500}     ← 上电回中位
15:35:00.350 -> {"angle":0,"duty":410,"us":500}
15:35:03.641 -> {"angle":180,"duty":2048,"us":2500}
15:35:07.719 -> {"angle":90,"duty":1229,"us":1500}
15:35:11.205 -> {"angle":160,"duty":1866,"us":2278}
15:35:14.990 -> {"angle":30,"duty":683,"us":834}
15:35:17.491 -> {"angle":0,"duty":410,"us":500}
```

判读：

1. **`attach=OK`** —— 14 位 PWM 起来了。这一行的有无能直接区分板子上跑的是不是当前固件。
2. **duty 与角度一一对应**，全部落在 14 位公式上：`160° → 500+2000×160/180 = 2278us → 2278×16384/20000 = 1866`；`30° → 834us → 683`。视频里舵机跟着这 6 条指令依次转到位。
3. **任意角度都成立**，不只是 0/90/180 三个刻度 —— 说明映射是连续的线性换算，不是查表。

#### 板子上的固件不是当前文件时，duty 会露馅

分辨率写错时 `ledcAttach` 返回 false 却不打日志，串口照常打印角度和 duty，舵机纹丝不动。此时的 duty 是按错误分辨率算出来的：

| 角度 | 14 位（正确，×16384/20000） | 16 位（×65536/20000，S3 上静默失败） |
|---|---|---|
| 90° | `1229` | `4915` |
| 180° | `2048` | `8192` |
| 10° | `501` | `2002` |

串口出现 `4915` / `8192` 这种明显偏大的 duty，就说明烧进去的还是旧固件，重新上传即可。

## 九、与《逐日指南》的出入

| 项 | 《逐日指南》 | 本项目 |
|---|---|---|
| PWM API | `ledcSetup` / `ledcAttachPin`（旧） | `ledcAttach` / `ledcWrite`（Core 3.x） |
| 分辨率 | 16 位（初代 ESP32 参数） | **14 位** —— S3 的 `SOC_LEDC_TIMER_BIT_WIDTH` 上限；写 16 静默失败 |
| 供电 | 未提及 | SG90 需 5V，红线不能接 3V3；堵转 700mA 会拖垮 USB |
| 引脚 | GPIO18 | GPIO18（避开 strapping 0/3/45/46、Flash/PSRAM 26~37、USB 19/20） |
| 摆动速度 | 未指定 | 每格 300ms，够 SG90 走完 180°（约 0.1s/60° → 全程约 0.3s） |
| 信号线颜色 | 橙色 | 本器件实物是**黄色**。线色不统一，别按颜色认线 —— 按"两端中排"的位置认 |
