## 一、两套行为抢同一组电机

Day 27 的车只能人开，Day 21 的车只能自己跑，两套代码都直接调 `drive()`。合成一个固件，第一个要定的不是按钮长什么样，是**谁说话算数**。

答案只能是板子上一个状态：`cmdMode`。它只有两个值，上电是 `MODE_MANUAL`——**自动是一次明确的点击，不是上电默认态**（Day 27 要点 ③ 的同一条：插电那一瞬车不许动）。

定了这一个状态源之后，剩下三处都要为它让路：

**① 自动时方向键收下但不执行。** `handleCmd()` 里 `dir` 照常校验、照样返回 200，就是不往电机上写。为什么不直接回 400 拒掉？因为面板的心跳里还带着 `dir`（手动按住时心跳发的是 `dir=fwd`），拒掉会让心跳失效，看门狗反手把车停住——一个显示层的细节把安全机制带歪了。

**② 切回手动必须先停车。** `setMode(MODE_MANUAL)` 第一件事是 `stopAll()`。否则自动正在前进的那一脚油门，会接着手动的 `cmdDir` 继续跑，表现是"退出自动了车还在走"。

**③ 灯色不能撞车。** 手动和自动共用板载那一个 RGB：

| | 绿 | 橙 | 红 | 黄 | 品红 | 蓝 | 暗 |
|---|---|---|---|---|---|---|---|
| 手动 | 前进 | 后退 | — | — | 左转 | 右转 | 停 |
| 自动 | 直行 | 后退 | 转向 | 定向前进 | — | — | — |

绿和橙两种模式下含义一致（都在往前/往后跑），照用；**红色只留给自动转向**，于是脱离 USB 时看灯就能分辨"现在是谁在开"，不用猜。

## 二、看门狗保护的是模式，不只是方向

这是本固件最重要的一个决定。

Day 27 的看门狗语义是"超过 1 秒没收到指令就停"。自动模式下乍一看该把它关掉——人又没在打方向，凭什么要求心跳？

不能关。想清楚为什么：**自动模式是唯一一种"车在跑而人没在操控"的状态**。人在屋里跟着车走，Wi-Fi 一掉，手机上没有任何办法让它停——方向键按了没人执行，停止键点了也发不出去。手动模式下同样的故障只是"车停了"，自动模式下是"车以巡航速度跑到没电"。

所以心跳的含义从"人在打方向"扩展成：

> **人还在，并且还要这个模式。**

心跳照发，只是内容从 `dir=fwd` 换成 `beat=1`——一句不带任何参数的"我还在"。看门狗一行代码没改，它保护的对象自动从"方向"覆盖到了"模式"：Wi-Fi 掉了 → 刹车 + **退回手动**，等手机连回来看到的是一个干净的停车态，而不是一个还在跑但谁也拦不住的自动模式。

代价是自动模式没法"人走开、车自己跑"。手机锁屏、切后台都会让页面隐藏，页面一隐藏就发 `mode=manual`——这是 Day 27 就立过的规矩（"用户松手了"这件事浏览器不保证告诉你），今天只是把它推广到了模式上。要真的无人值守跑，得等后面把自主行为做进固件，那时候车不该再依赖一部手机活着。

## 三、心跳什么时候该跑

规则一句话：**手动时"按住方向键"算有人在开，自动时"自动开着"算，其余一律不发。**

```js
function needBeat() { return holding !== null || mode === 'auto'); }
function syncBeat() {
  if (needBeat() && beat === null) { sendBeat(); beat = setInterval(sendBeat, BEAT_MS); }
  else if (!needBeat() && beat !== null) { clearInterval(beat); beat = null; }
}
```

`syncBeat()` 在四处被调用：按下、松手、切换模式、每次 `/data` 回来。最后那一处是关键——**模式以板子说的为准**。上一轮要是被看门狗踢回了手动，按钮会在 500ms 内自己变回去，不会出现"按钮还亮着自动、车其实停着"的骗局。

空闲的手动模式不发心跳：那时车停着，`carMoving` 是 false，看门狗看了也不会动作，发了只是白占带宽。

## 四、测距节奏取严的那个，串口退成只报决策

两处细节因为"合成"而必须重新定：

**测距间隔 200ms → 100ms。** Day 27 用 200ms 是因为它只喂面板（面板自己 500ms 才拉一次），Day 21 用 100ms 是因为它要驱动避障决策。100ms 是两者中严的那个，统一取 100ms：手动时只是多测两次，自动时才有足够快的反应。

**串口不再每 500ms 报距离。** Day 21 每小时打一行"前方 xx cm，通畅"，今天不打了——面板上距离一直在跳，串口该留给别的东西：为什么转、往哪转、什么时候停、什么时候被踢回手动。当人有更好的输出通道时，旧的通道要退成只报决策。

```text
模式 → 自动避障
第1轮｜前方 12.4cm < 15cm，挡住了 → 后退 500ms
第1轮｜原地左转 400ms（左右交替，下一轮换另一边）
第1轮｜转向已转开，强制前进 300ms 再重新测距
模式 → 手动（已停车）
⚠ 1000 ms 没收到指令，已刹车（第 1 次）
⚠ 自动模式已退回手动
```

**后退/转向那几段面板上的距离是不刷新的**，停在进入避障那一刻的值，最多停 1.2 秒。这不是 bug：转身的时候测到的是侧面的墙，拿它判断"前方通没通"是错的。

速度滑块在自动模式下也是活的：`reapplyAutoDuty()` 让改动立刻作用到当前这一段，不等下一次状态切换。只有转向那一段用固定 `DUTY_TURN`——Day 27 定过，转向不跟滑块走。

## 五、测试结果

**固件编译**：`arduino-cli compile --fqbn esp32:esp32:esp32s3` 干净通过，975804 字节（74%），无警告。比 Day 27 多 38948 字节，是状态机、新模式的路由分支和面板上那个开关。

**控制面板（电脑上实测）**：同样的办法——把 `R"rawliteral(...)rawliteral" 抽出来，起一个 mock `/cmd` / `/data`，用合成 PointerEvent 走一遍。这一轮的 mock 会"说谎"（`/data` 里返回的 `mode` 可随时改），专门用来验面板是否以板子为准：

| 场景 | 期望 | 实测 |
|---|---|---|
| 点「自动避障」 | 一条 `mode=auto` + 心跳开始 | `mode=auto`、`beat=1` ✅ |
| mock 说"我在自动模式" | 按钮变「自动中」、高亮、状态行显示 `自动·直行` | 三项全变 ✅ |
| 自动模式下按方向键 600ms | **一条 `dir` 都不发**，只有心跳 | 仅 `beat=1` ×2 ✅ |
| 自动模式中页面隐藏 | 立刻 `mode=manual`，心跳停 | ✅ |
| 手动空闲 700ms | 一个请求都不发 | 空 ✅ |
| 速度滑块 | 恰好一条 `speed=160` | 一条 ✅ |
| 按住 back 700ms | 首条 + 250ms 一条心跳 | `dir=back` ×3 ✅ |
| 松手 | 立刻 `dir=stop`，再无请求 | ✅ |

**整车上机**：手动遥控与自动避障都在真机上跑通，演示视频见 §六。

|---|---|---|

| 约 20–25 s | 再点一次 → 按钮变回「自动避障」 | 立刻停，回到干净的手动停车态 |

### 接头是这条链路的隐性门槛

这条视频是**把线重新固定、该焊的焊好之后**录的。Day 24 到 Day 27，车上一直是面包板 + 杜邦线的状态：能跑，但每个接头都是一个"偶尔能用"的点。Day 18 记过同一个形状的坑——`mpu.begin()` 报 `not found`，而同一条线上扫描器能扫到 0x68，最后查出来是母头没插到底、接触不良；扫描是偶发成功，库初始化要求连续成功，所以"扫描能过"不等于"接触可靠"。

放到这个项目上结论是同一条：**Wi-Fi 遥控 + 自动避障是一条要求连续成功的链路**——看门狗要 1 秒内收到心跳，超声波要每 100 ms 出一周。中间任何一处接触不良，都会表现成"看着像软件问题"的症状：掉线、超时停车。所以接头该焊就焊，这不是美观问题，是可靠性问题。

> 📌 录视频时车是自由的（没 USB 线），串口全程拿不到。所以每条验收都得能不依赖串口地看出来：灯色、面板上的状态行和距离读数、按钮文案、录屏本身。
