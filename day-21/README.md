## 一、今天和 Day 19 的关系

Day 19 解决"让一个电机转起来"，今天解决"让两个电机协同起来，并且知道自己该往哪走"。

| | Day 19 | Day 21 |
|---|---|---|
| 电机数 | 1（只用 A 通道） | 2（A + B 全用上） |
| 控制目标 | 转速 | **车体运动**：直行 / 转向 / 弧线 |
| 有感知吗 | 无 | HC-SR04 测前方距离 |
| 是闭环吗 | 开环（发出 duty 就完事） | **外环闭环**：测距 → 判断 → 动作 → 再测 |
| 代码组织 | 一个 `setMotor()` | 运动函数 + 状态机 |

底盘套件自带的两个 TT 马达**没有编码器引线**，所以轮子转速依然是开环 —— 今天的"闭环"闭的是**避障决策**那一层，不是转速。真正的转速闭环要等编码器（Day 28 前后）。

### 为什么是差速转向

两轮车没有转向机构。想拐弯只能让两个轮子转速不同：

```
直行      左 ●▶▶▶▶  右 ●▶▶▶▶        同速同向 → 直线
原地左转  左 ◀◀◀●    右 ●▶▶▶▶        等速反向 → 绕车体中心转，半径 ≈ 0
弧线左转  左 ●▶▶     右 ●▶▶▶▶        同向不同速 → 绕远处圆心走弧
```

三种转向里**原地转向最常用**：转弯半径为零，能在死胡同里掉头。代价是两个轮子互相较劲，电流比直行大。

指南没给这个分类，只写了 `turnLeft(speed)` / `turnRight(speed)`，实际实现里两者都是原地转向。代码里把三种都做了，因为弧线是"边走边修正方向"的基础 —— 后面想让车沿墙走就得靠它。

### 三条和 Day 19 相同的线

**① 共地。** 电池负极、ESP32 GND、TB6612 GND、HC-SR04 GND 四者连一起。Day 19 和 Day 17 各自强调过一次，今天两组电路合体，漏接的表现是"电机不动且测距恒为 0"。

**② VM 和 VCC 仍是两路独立电源。** VM 走电池（电机电流，几百 mA），VCC 走 ESP32 3V3（逻辑，几 mA）。电机电流不经过开发板。

**③ 电池盒装 4 节（6V）。** 套件 TT 马达额定 3V，靠占空比把平均电压压回 3V 以内 —— 见 §三。选 6V 不是为更快，是为**更低内阻**：两路电机同时启动时的峰值电流，2 节 5 号根本供不出来。

## 三、duty 从哪来：为什么是"6V 电源 + 半占空比"

指南的 `leftMotor.drive(150)` 是从"8 位 PWM、占空比过半就该转"的直觉来的。Day 19 实测过这个直觉是错的。

### 平均电压才是判据

电机线圈是电感，电流被平滑，吃到的不是 PWM 峰值而是**平均值**：

```
平均电压 = 电源电压 × 占空比
```

所以同一颗马达，两套供电给到完全一样的平均电压：

| 供电 | 占空比 | 平均电压 |
|---|---|---|
| 3V（2 节 5 号）× 230/255 | 90% | 2.7V |
| 6V（4 节 5 号）× 115/255 | 45% | **2.7V** |

马达受力、发热、转速三者完全相同 —— 6V 峰值不会烧马达。**这是用高压电源驱动低压电机的标准做法。**

### 那为什么还要换 6V

因为**内阻**。

TT 马达启动瞬间处于堵转状态，电流最大。2 节 5 号的电池内阻相对 3V 这个电压太大，一个电机启动就把电压拉垮，两个一起启动直接掉到转不起来：

```
3V 供电，两个电机同时启动
  → 电池电压被拉垮 → 只嗡嗡响不转
  → 或者一个先转起来（电流下降后）另一个才转 → 看着像"一先一后"
  → 电量稍降就时好时坏
```

换成 4 节 5 号，电压翻倍、内阻相对可忽略，PWM 导通瞬间的**峰值电流**大得多，顶得开静摩擦。平均电压没变，变得是"能不能供出启动那一下的电流"。

> 📌 **判据要分清是"电压不够"还是"电流供不出"。** 平均电压决定转速和发热；峰值电流决定能不能起转。3V 盒是后者不满足 —— 这也是为什么单轮测试（只带一个电机）在 3V 下也能转，两轮一起来就不行。

### 标定值

| 参数 | 3V 供电 | 6V 供电 | 理由 |
|---|---|---|---|
| 巡航 | 230 | **115** | 留一档余量 |
| 转向 | 240 | **120** | 原地转向两轮反向互相较劲，负载最大 |
| 慢速（弧线内轮） | 150 | **75** | 故意压在起转点以下，见下 |
| 起步冲击（200ms） | 255 | **150** | 短暂高于额定，只为顶开静摩擦 |

代码里两套值由 `supply6V` 切换，串口输 `v` 可运行时换标定，不用重新烧。**默认 6V。**

`DUTY_SLOW`（弧线内轮）是刻意压低的：它让内轮处于"通电但转不动"的边界，车体靠外侧轮拖着内轮走，弯会很急。实测如果内轮完全不动、车抖得厉害，就提高它。**这个数必须上机调，别指望算出来。**

### 起步冲击

两个轮子同时启动时，先各给一档高于目标的 duty 持续 200ms，再一起降到目标值：

```cpp
void kickStart(int left, int right) {
  int k = dutyKick();
  if (left)  driveMotor(AIN1, AIN2, PWMA, left  > 0 ?  k : -k);
  if (right) driveMotor(BIN1, BIN2, PWMB, right > 0 ?  k : -k);
  delay(KICK_MS);
  driveMotor(AIN1, AIN2, PWMA, left);
  driveMotor(BIN1, BIN2, PWMB, right);
}
```

不加这一段时，两个轮子从静止直接上目标 duty，容易卡在静摩擦上嗡嗡响。短暂超压只持续 200ms，马达来不及发热。

### PWM 频率取 20kHz 而不是 5kHz

一是**超出人耳范围**，消除 PWM 啸叫。之前听到的"电机响"有一部分就是它，容易和"堵转转不动"的嗡嗡声混淆，排查时特别误导。二是周期变短，电机线圈的电流纹波更小，平均电压更接近理论值。

### 两个马达不一样快

套件里两个 TT 马达存在个体差异：同样的 duty，转速不同，直行会跑偏。这是开环控制的固有缺陷，代码里留了补偿位：

```cpp
const int TRIM_RIGHT = 0;   // 车往左偏 → 右轮慢 → 加正数补偿
```

实测车往哪边偏，就给另一边的 duty 加几个点。这是**手工标定**，不是自适应 —— 真正的解法是编码器闭环（Day 28 前后）。

### 运动函数怎么组织

把"一个电机怎么转"和"车体怎么动"分成两层：

```cpp
// 底层：单个电机，speed = -255 ~ +255
void driveMotor(int in1, int in2, int pwmPin, int speed);

// 上层：车体运动，翻译成左右轮各给多少
void setMove(Move m) {
  switch (m) {
    case M_FORWARD: rl =  DUTY_CRUISE; rr =  DUTY_CRUISE; break;
    case M_PIVOT_L: rl = -DUTY_TURN;   rr =  DUTY_TURN;   break;   // 反向
    case M_ARC_L:   rl =  DUTY_SLOW;   rr =  DUTY_CRUISE; break;   // 降速
    ...
  }
  driveMotor(AIN1, AIN2, PWMA, rl);
  driveMotor(BIN1, BIN2, PWMB, rr);
}
```

分层的好处是**转向逻辑只写一遍**：想改"左转是原地还是弧线"，只动 `setMove` 里的两个数，不用碰 H 桥真值表。

### 两路 LEDC 不会打架

指南的 `Motor` 类有个真实的 bug：

```cpp
class Motor {
private:
  int _channel = 0;      // ❌ 两个实例都是通道 0
};
Motor leftMotor(10, 11, 12, 16);
Motor rightMotor(13, 14, 15, 16);
```

两个实例的 `_channel` 都硬编码成 0，`ledcSetup(0, ...)` 被调用两次、参数相同还好，一旦想给两路不同频率就会互相覆盖。旧 API 按**通道号**寻址，通道号得自己管。

Core 3.x 的 `ledcAttach(pin, freq, res)` 按**引脚**分配，底层自动挑空闲通道：

```cpp
ledcAttach(PWMA, 20000, 8);   // 自动占一个通道
ledcAttach(PWMB, 20000, 8);   // 自动占另一个
```

两行就够，不存在抢通道的问题。

### 别用 `ledcRead()` 回读

调试时想确认"占空比到底写进去没有"，第一反应是 `ledcRead()`。实测它在 Core 3.x 的部分版本**恒返回 0**，与写入值无关：

```
刹车时 ledcWrite(PWMB, 255);
串口打印 PWMA=0% PWMB=0%     ← 假的，实际是 100%
```

这个假象差点让我们误判成"PWM 没生效、B 通道坏了"。**打印写入值，不要打印回读值。**

### 刹车和滑行仍然要分清

Day 19 那张真值表今天完全沿用，**两个电机各执行一次**：

| 想要 | IN1 / IN2 | PWM |
|---|:---:|:---:|
| 刹车（立刻停住） | `1 / 1` | **必须非 0** |
| 滑行（靠惯性停） | `0 / 0` | 0 |

`PWM = 0` 时输出是高阻，与 IN 无关。所以"IN1=IN2=1 但 PWM=0"依然是滑行 —— 这个坑在 Day 19 踩过一次，今天两个电机就是两次机会踩。

序列末尾专门留一个刹车档，是为了把"两轮短接立刻停住"和"两轮断电靠惯性慢停"放在同一段演示里对比着看 —— 滑行档松手后车还会溜一段，刹车档是原地定住。

接线实物：[`超声波避障接线实物图.png`](./超声波避障接线实物图.png) ｜ 串口打印：[`实验2-超声波避障-串口打印.txt`](./实验2-超声波避障-串口打印.txt) ｜ 视频：[`实验2-超声波避障.MOV`](./实验2-超声波避障.MOV)

### 状态机

避障不是"看到障碍就转"，是一串**有先后顺序的定时动作**：

```
CRUISE ──cm < 15──▶ BACK ──500ms──▶ TURN ──400ms──▶ COMMIT ──300ms──▶ CRUISE
   ▲                                                                     │
   └────────────────────── cm ≥ 15 ──────────────────────────────────────┘
```

| 状态 | 动作 | 灯色 | 为什么需要这一段 |
|---|---|---|---|
| `CRUISE` | 直行 + 每 100ms 测距 | 🟢 绿 | 唯一会测距的状态 |
| `BACK` | 后退 500ms | 🟠 橙 | 先拉开距离，贴着障碍转向会刮蹭 |
| `TURN` | 原地转向 400ms | 🔴 红 | 换方向 |
| `COMMIT` | **强制前进** 300ms | 🟡 黄 | 不看测距，先开出去再说，见下 |

`COMMIT` 这一段是指南没有的。没有它的话，转完立刻回到 `CRUISE` 开始测距，可能刚转了 40° 又看到同一堵墙，于是再退再转 —— 车会贴着墙原地抽搐。强制前进 300ms 让它先离开障碍区，再恢复判断。

### 阈值必须带迟滞

指南写的是 `if (dist > 0 && dist < 15)` 单一阈值。单一阈值在临界点上会**振荡**：

```
退到 16cm → 判断通畅 → 前进
进到 14cm → 判断挡路 → 后退
退到 16cm → ...
```

车会卡在 15cm 附近反复前后抽搐。改法是用两个阈值：

```cpp
const float NEAR_CM = 15.0;   // 进入避障
const float FAR_CM  = 25.0;   // 退出避障
```

`cm < 15` 进避障，`15 ≤ cm ≤ 25` 保持现状（不动），`cm > 25` 才确认通畅。中间 10cm 的**死区**让状态稳住 —— 这就是迟滞（hysteresis），和 Day 14 数字电压表里的阈值判断是同一个思路。

### `pulseIn()` 的阻塞被压到 1/5

Day 17 就记过一笔：`pulseIn()` 阻塞等待回波，超时参数是 30ms（对应 400cm 量程），最坏情况下 `loop()` 会卡住 30ms。

避障场景只关心 15cm 以内，所以把超时压到 6ms（≈ 103cm）：

```cpp
const unsigned long TIMEOUT_US = 6000;   // 而不是 Day 17 的 30000
```

超时的结果是"前方很远"，与远距结论一致 —— 反正都是前进，没有任何信息损失，但最坏卡顿从 30ms 降到 6ms。

> ⚠️ 这只是**缓解**，不是根治。真要严格非阻塞得用定时器的输入捕获（ICP）或中断 + `micros()`。今天 6ms 的卡顿对 100ms 的测距周期来说是 6%，可以接受。

### 读数下限

模块标称下限 2cm。低于此值发射脉冲还没结束就收到回波，读数不可信。代码里低于 2cm 一律按"通畅"处理 —— 因为车不可能已经贴到 2cm 才第一次发现障碍，这种读数必然是异常值。

### 为什么要左右交替转向

`TURN` 的转动方向由 `turnLeftNext` 决定，**每完成一次转向就翻一次边**：

```cpp
if (turnLeftNext) drive(-DUTY_TURN,  DUTY_TURN);   // 左转
else              drive( DUTY_TURN, -DUTY_TURN);   // 右转
...
turnLeftNext = !turnLeftNext;    // 下次换另一边
```

第一次挡路左转、第二次挡路右转、第三次左转……所以看到"一会儿左拐一会儿右拐"是**设计如此**，不是随机。固定朝一边转的话，遇到走廊或夹角会一路朝同一方向越转越深，最后贴着墙出不来；交替转相当于在原地附近来回试探，总能找到一条出去的路。

代价是它不"记住"哪边是出路 —— 真正的解法要加第二个传感器或做建图，今天只做到"能脱困"。

### 手一直挡着就会一直避障

手停在 15cm 处不动，车的行为是**反复触发避障，不是卡死**：退 0.5 秒 → 转 0.4 秒 → 强进 0.3 秒 → 回到 `CRUISE` 测距 → 手还在那儿 → 又触发。一轮约 1.2 秒，左右交替，所以看起来是"连续地退和拐弯"。

这不是 bug，是闭环在诚实地工作：**障碍一直存在，就得一直绕**。真正的"停下来"要靠别的状态（比如连续 N 轮都脱不了困就判定为死胡同），今天没有做。

### 串口输出为什么写中文

按 Day 13 的约定，串口该输出 JSON 裸数字：

```
{"cm":12.3,"state":"BLOCKED"}
{"cm":31.2,"state":"CRUISE"}
```

但避障是**一串连续动作**，光看一行数字看不出"现在是第几步、为什么转、往哪边转"，通畅时还会每 100ms 刷一行把有效信息淹掉。所以这里改成中文整句，并且在**状态切换的那一刻**打印原因：

```
前方 31.2cm，通畅 → 直行前进
第1轮｜前方 12.3cm < 15cm，挡住了 → 后退 500ms
第1轮｜原地左转 400ms（左轮后退 / 右轮前进，左右交替，下一轮换另一边）
第1轮｜转向已转开，强制前进 300ms 再重新测距（避免刚转开又看到障碍）
第2轮｜前方 9.8cm < 15cm，挡住了 → 后退 500ms
第2轮｜原地右转 400ms（左轮前进 / 右轮后退，左右交替，下一轮换另一边）
```

通畅时按 `LOG_MS = 500` 节流，状态切换时立刻打印。`第N轮` 是连续避障的计数，直接回答"为什么一直在转"。

> 原则：日志要解释**为什么**，不只是**是什么**。调试时真正卡人的从来不是"值是多少"，而是"它凭什么做了这个决定"。JSON 留给 Python 解析（Day 13/14/17 的数据采集场景），人看的现场日志另写一套。

> ⚠️ **时长用毫秒整数打印，不要用 `%.0f` 秒。** 第一版写成 `%.0f 秒` + `500/1000.0`，实测串口打出来全是"后退 0 秒""左转 0 秒" —— `%.0f` 会把 0.5 四舍五入成 0。时长这类**小于 1 秒的量**，格式化成秒就丢信息，直接打毫秒。

### 实测记录

八轮连续避障的串口片段（手在车前方反复挡）：

```

前方通畅：超出量程（>100cm），继续直行
第1轮｜前方 6.1cm < 15cm，挡住了 → 后退 500ms
第1轮｜原地左转 400ms（左轮后退 / 右轮前进，左右交替，下一轮换另一边）

前方 16.2cm，通畅 → 直行前进
第2轮｜前方 14.8cm < 15cm，挡住了 → 后退 500ms
第2轮｜原地右转 400ms（左轮前进 / 右轮后退，左右交替，下一轮换另一边）
```

三个可以直接读出来的结论：

| 现象 | 说明 |
|---|---|

## 六、实验 3：串口单步调试

[`实验3-串口单步调试.ino`](./实验3-串口单步调试/实验3-串口单步调试.ino)

实验 1 是自动轮播序列，出问题时要等它转一圈才能重看某个动作。实验 3 改成**串口输命令、一次只做一个动作**，每个动作都能反复单独测。

| 命令 | 动作 | 灯 |
|---|---|---|
| `1` / `2` | 两轮前进 / 后退 | 绿 / 橙 |
| `3` / `4` | 原地左转 / 右转 | 青 / 紫 |
| `5` / `6` | 左弧线 / 右弧线 | 黄 / 黄 |
| `7` / `8` | 两轮刹车 / 滑行 | 红 / 蓝 |
| `9` | 右轮连测（左轮断电，前进 3s → 后退 3s） | 绿→橙 |
| `lf` `lb` `lz` `lc` | 左轮 前进 / 后退 / 刹车 / 滑行 | 绿 / 橙 / 红 / 蓝 |
| `rf` `rb` `rz` `rc` | 右轮 前进 / 后退 / 刹车 / 滑行 | 绿 / 橙 / 红 / 蓝 |
| `s` | 占空比扫描：两轮同时 80→255，每档 1.5s | — |
| `v` | 切换 6V / 3V 占空比标定 | — |
| `0` | 立刻断电 | 灭 |

单轮四态**另一路全程断电**，这样只看目标轮。刹车和滑行会**先前进 2 秒再执行** —— 静止的轮子看不出刹车和滑行的区别。

每条命令都打印 6 根 GPIO 的电平与平均电压：

```
绿灯 | 前进  两轮都向前 | 左轮=前进115 右轮=前进115 | 跑 6 秒
  输出 → AIN1=1 AIN2=0 | BIN1=1 BIN2=0 | PWMA=45%(2.7V) PWMB=45%(2.7V)
红灯 | 刹车 1 秒
  刹车 → AIN1=1 AIN2=1 | BIN1=1 BIN2=1 | PWMA=100%(6.0V) PWMB=100%(6.0V)
```

`2.7V` 那一项可以直接拿万用表直流档量电机两端对一下。

### 排查记录：两个轮子"时好时坏"

上机时遇到一串症状，看起来像软件 bug，实际都不是：

| 现象 | 真实原因 |
|---|---|
| 只有左轮转 | 3V 电池内阻太大，两轮同时启动抢电流 |
| 一阵子左、一阵子右 | 同上 —— 先转起来的那个电流下降，才轮到另一个 |
| 红灯刹车时右轮还在转 | 同上；且 `ledcRead()` 恒返回 0 制造了"PWM 没生效"的假象 |
| 原地转向只有左轮转 | 转向负载最大，3V 更供不出 |
| 电机响但不转 | 堵转嗡嗡声 + 5kHz PWM 啸叫混在一起 |

**定位的关键一步是单轮测试**：`lf lb lz lc rf rb rz rc` 八条全过，说明六个 GPIO、TB6612 两路、两个电机、全部接线都正常。而 `1-8`（两轮 + 低占空比）全都不转。两组测试只差**轮子数**和**占空比**，于是锁定电源 —— 换成 6V 电池盒后全部命令一次通过。

> 📌 **症状相似时，找一个"只差一个变量"的对照组。** 这次的对照组就是"单轮 vs 双轮"。如果先入为主认定是 GPIO 接触不良，会一直在 6 根杜邦线上打转。

## 七、上机检查点

| 现象 | 判断 |
|---|---|
| 两个电机都转，但车跑偏 | ✅ 正常，两个马达有个体差异。调 `TRIM_RIGHT` 补偿 |

| 车跑一会儿明显变慢 | 电池电压下降。开环调速的固有表现，见 §三 |

### 为什么 TRIM_RIGHT 现在做不了

标定需要车**自由跑至少 2 米**，而 USB 线既供着电又拴着车：线一拽，跑偏量的判断全是线缆干扰，量出来的补偿值没有意义。想自由跑就得脱离 USB，脱离 USB 就没有串口。

所以真正要问的不是"什么时候有空标"，而是**脱离 USB 后数据怎么回电脑**。答案是走 **Wi-Fi**（Day 25）：ESP32-S3 自带 Wi-Fi，连家里路由或自建 AP，Python 端用 socket 收，不需要额外硬件。BLE 要装 `bleak`、蓝牙串口模块要另买、SD 卡模块手头没有，都不如 Wi-Fi 直接。

于是顺序只能是：

```
Day 24  MP1584EN 到货 → 车脱离 USB（能自由跑了，但没有数据通道）
Day 25  Wi-Fi 打通     → 数据能回电脑了
Day 25+ 才有条件标定   → 下发 trim、读回轨迹，一次搞定
```

> 📌 标定**不阻塞任何事**：车跑偏只是直行不直，避障闭环完全正常。所以可以等。

> 📌 连带影响：Day 26 指南写的"串口实时绘图"到那天很可能已经没有串口可用了 —— 车一旦脱离 USB，实时绘图也得改成收 Wi-Fi 数据。`serial_logger.py` 的解析与落 CSV 逻辑不用改，只需把 `serial.Serial()` 换成 socket 读。**注意 ADC2（GPIO11-20）与 Wi-Fi 冲突，Day 25 起模拟量一律走 ADC1（GPIO1-10）。**

### 成品化供电：脱离 USB（MP1584EN 降压模块）

目前 ESP32 靠 USB 供电，车被一根线拴着。降压模块到货后按此接法断开 USB：

```
6V 电池盒
   ├────────────────────► TB6612 的 VM（电机动力，直连 6V，不经降压）
   │
   └──► MP1584EN IN ──► OUT 5V ──► ESP32「5V」引脚
                                    │
   电池负极 ──┬── TB6612 GND ───────┴── ESP32 GND   （三点共地）
```

⏳ 待降压模块到货后落地（2026-09-22 下单，运输中）：

1. 万用表量 MP1584EN 输出端，确认真是 5V 再上板
2. 6V 电池盒正负极各引出两路：一路进 TB6612 VM，一路进降压模块 IN
3. 降压 OUT 5V → ESP32「5V」引脚，负极 → GND，**三点共地**
4. 先不拔 USB，量完电压再拔；拔掉后串口监视器会断，属正常
5. 车放地上跑，复测 `TRIM_RIGHT` 与电压跌落

> ⚠️ **电机不能走降压模块。** 两个 TT 马达同时启动的堵转电流会超过 MP1584EN 的 3A，模块过流保护会打嗝，正是 Day 21 §三 踩过的"电流供不出"那个坑。所以 6V 是**并联两路**：电机直连，只有 ESP32 走降压。
>
> ⚠️ **必须共地**，否则 TB6612 的 PWM 信号没有回流路径，电机完全不听使唤。
